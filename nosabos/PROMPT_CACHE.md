# Prompt and Response Caching Plan

Handoff document for reducing Gemini and OpenAI latency and input-token cost
without making lessons stale, repetitive, or less personalized.

This is a plan only. It does not authorize broad response caching, prompt
rewrites, or changes to lesson behavior.

## Goal

Improve model-call efficiency by:

1. Measuring the automatic prompt caching already provided by Gemini and
   OpenAI.
2. Restructuring eligible prompts so repeated static prefixes can produce more
   cache hits.
3. Adding provider-specific cache controls only where measurements show a
   benefit.
4. Caching completed artifacts only when their inputs and invalidation rules
   are deterministic.

The desired outcome is lower latency and cost with no observable reduction in
answer quality, personalization, freshness, or correctness.

## Non-goals

- Do not return an old model response merely because a similar prompt was seen.
- Do not cache Tutor conversation replies, adaptive feedback, grading results,
  or learner-specific explanations across users.
- Do not let cached content bypass lesson, entitlement, authentication, or App
  Check boundaries.
- Do not place prompt bodies, model responses, or growing cache maps in the
  main user document.
- Do not introduce explicit provider caches before automatic cache behavior is
  measured.
- Do not change models as part of a caching-only implementation.
- Do not treat a cache hit as proof that a response is correct.

## Important distinction

### Provider prompt/context caching

Gemini and OpenAI can reuse internal processing for an identical prompt prefix.
The model still generates a fresh response. This should not make the UX stale
or cause repeated answers by itself.

### Application response caching

The app stores and returns an already generated artifact. This can save the
entire model call, but it is safe only when every output-affecting input is
represented in the cache key and invalidation is explicit.

The implementation should optimize provider caching first. Full-response
caching should remain narrow and feature-specific.

## Current state (2026-07-24)

### Gemini

- Shared model calls use Firebase AI Logic with the Vertex AI Gemini API.
- `callResponses()` tries Gemini first through
  `generateContentStream()` and falls back to OpenAI after a Gemini failure.
- Firebase/Gemini implicit context caching may apply automatically to eligible
  repeated prefixes.
- The app does not create or reference an explicit Gemini content cache.
- The app does not record Gemini's cached-token metadata.

Model configuration currently lives in:

```text
src/firebaseResources/firebaseResources.js
```

The configured name is currently `gemini-3.5-flash-lite`. Before caching work,
verify that exact model name against the models available to the Firebase
project. Current Firebase documentation lists `gemini-3.5-flash` and
`gemini-3.1-flash-lite`; caching work must not mask a model-configuration
failure.

### OpenAI

- The shared fallback uses `gpt-5-nano` through the Responses API proxy.
- Some product surfaces call the OpenAI Responses API directly as their primary
  text model path.
- OpenAI automatic prompt caching can apply to eligible requests with long,
  identical prefixes.
- The app does not currently send `prompt_cache_key`, explicit cache
  breakpoints, or a cache retention policy.
- The app parses the generated text but does not retain or report
  `cached_tokens` or cache-write metrics.

Relevant files:

```text
src/utils/llm.js
functions/index.js
```

### Existing application caches

The repository already has a few bounded caches that should remain independent
from provider prompt caching:

- Generated TTS audio uses memory and IndexedDB caching with a seven-day TTL.
- Some prepared RPG content is stored in `localStorage`.
- Some features use in-memory maps to deduplicate simultaneous requests.

These examples do not constitute a generic model-response cache.

## Product invariants

### UX

- A provider cache hit must not change the generated answer contract.
- Personalized or conversational calls must still include current learner and
  session state.
- Cache misses and cache service failures must transparently fall back to a
  normal model request.
- The user must never wait for cache maintenance before receiving a response.
- Streaming behavior must remain available.

### Correctness

- Cache keys must include every value that can materially change a cached
  artifact.
- Prompt-template changes must invalidate old application caches.
- Model changes must not reuse response artifacts generated by another model
  unless explicitly validated.
- A locale, target language, CEFR level, lesson, activity mode, or curriculum
  version change must not reuse an incompatible artifact.
- Grading and progress writes must never depend on a cross-user cached answer.

### Storage

- Do not store cache data as a growing field on `users/{uid}`.
- Browser-only caches must use bounded storage with a TTL and size/entry cap.
- Persistent shared cache metadata, if eventually needed, must use a dedicated
  collection or backend cache service.
- Per-user persistent cache metadata, if needed, must use a dedicated
  subcollection such as `users/{uid}/modelCacheEntries/{cacheKey}` rather than
  the main user document.
- Provider-managed prompt caches should remain provider-managed; do not mirror
  prompt contents into Firestore.

### Privacy and security

- Never log raw prompts or responses solely for cache analysis.
- Metrics should contain operational metadata, not learner content.
- Do not put user IDs, emails, names, or raw lesson text in externally visible
  cache keys.
- Hash or bucket identifiers when a per-user cache boundary is unavoidable.
- Cache access must preserve the same authentication, authorization, App Check,
  and project boundaries as an uncached request.

## Phase 0 — Validate configuration and establish a baseline

**Risk:** Low  
**Behavior change:** None

### 0.1 Validate active model paths

- Confirm which calls are Gemini-first, OpenAI-first, and OpenAI fallback.
- Verify all configured Gemini model names against the Firebase project's
  available-model list.
- Verify the allowed OpenAI model list in the Cloud Function proxy.
- Record which provider and model actually served each audited request.
- Keep model corrections in a separate, reviewable change from cache
  optimization.

### 0.2 Build a prompt inventory

For every model-backed feature, record:

| Field | Purpose |
|---|---|
| Feature and operation | Identifies the user-visible call |
| Provider/model path | Gemini, OpenAI, or fallback |
| Static prefix size | Estimates cache eligibility |
| Dynamic inputs | Defines personalization and invalidation |
| Typical input tokens | Identifies meaningful cache candidates |
| Call frequency | Estimates potential savings |
| Reuse scope | Request, session, user, lesson, or global |
| Freshness requirement | Determines whether response caching is allowed |
| Failure fallback | Confirms cache-independent reliability |

Start with high-volume paths such as Tutor helpers, lesson activity generation,
Vocabulary, Grammar, Stories, History, RPG preparation, and grading.

### 0.3 Record an uncached baseline

Measure at least:

- Request count by feature, provider, and model.
- Time to first token and total response latency.
- Input, output, and reasoning tokens where available.
- Provider failures and fallback rate.
- Estimated input-token cost.
- Duplicate concurrent requests.
- Prompt-prefix size and stability.

Use a repeatable test set spanning multiple lessons, CEFR levels, target
languages, and support languages.

## Phase 1 — Add cache observability

**Risk:** Low  
**Behavior change:** None

Instrumentation should record:

```text
request ID
feature / operation
provider
model
prompt template version
input token count
cached input token count
cache-write token count, when reported
output token count
time to first token
total latency
success / failure / fallback
```

Provider mappings:

- Gemini: capture `cachedContentTokenCount` from response usage metadata.
- OpenAI Responses API: capture `usage.input_tokens_details.cached_tokens` and
  `cache_write_tokens` when available.

Requirements:

- Do not store prompt or response text in cache telemetry.
- Do not block the response on telemetry delivery.
- Sample or aggregate high-volume events.
- Add dashboards or structured logs that can calculate cache-hit rate and
  cached-token percentage by operation.
- Retain provider usage data in the proxy response long enough for the caller
  or backend logger to observe it.

Exit criteria:

- Cache metrics are visible for both providers.
- Gemini-to-OpenAI fallbacks are distinguishable from normal OpenAI-primary
  calls.
- At least one week or a representative test workload establishes the natural
  automatic-cache baseline.

## Phase 2 — Make prompts cache-friendly

**Risk:** Medium  
**Behavior change:** Intended to be none

For eligible operations, order prompt content as:

```text
stable product/system instructions
stable output contract or schema
stable rubric and examples
curriculum/lesson context
session context
learner-specific and request-specific input
```

Rules:

- Put stable repeated material first and dynamic material last.
- Preserve semantics; moving text must not change instruction priority.
- Avoid timestamps, random IDs, request IDs, and learner data in the shared
  prefix.
- Version each prompt template explicitly.
- Keep schemas and tool definitions byte-for-byte stable where practical.
- Do not pad short prompts merely to cross a provider's caching threshold.
- Snapshot representative outputs before and after reordering.

Suggested template identity:

```text
<feature>:<operation>:<prompt-version>:<model-family>
```

Example:

```text
lesson:vocabulary-generate:v3:gpt-5
```

Exit criteria:

- Regression tests show equivalent output contracts.
- Measured cache-hit rate or cached-token percentage improves.
- No statistically meaningful latency or quality regression occurs.

## Phase 3 — Optimize OpenAI prompt caching

**Risk:** Low to medium

Begin with automatic caching. Add a stable `prompt_cache_key` only for
operations that:

- Regularly exceed the provider's minimum cacheable input length.
- Share a genuinely identical prefix.
- Have enough request volume to benefit.
- Show avoidable cache misses in Phase 1 metrics.

Key guidance:

```text
piyali:<environment>:<feature>:<operation>:<template-version>:<prefix-variant>
```

- Do not include raw user data.
- Separate production, staging, and local development.
- Change the template version when the stable prefix changes materially.
- Partition keys if a single key's request rate becomes too high.
- Do not assume a key overrides exact-prefix matching.
- Use explicit cache breakpoints or retention controls only on models that
  officially support them.

For `gpt-5-nano`, first evaluate automatic caching plus a stable cache key.
Avoid adopting newer-model cache-write behavior or request fields without
confirming model compatibility and pricing.

## Phase 4 — Optimize Gemini context caching

**Risk:** Medium

### 4.1 Improve implicit caching

- Keep large shared instructions and curriculum context at the front.
- Keep identical prefixes byte-stable.
- Measure `cachedContentTokenCount`.
- Confirm the configured model supports caching through Firebase AI Logic.

### 4.2 Evaluate explicit content caches

Explicit Gemini caches should be considered only for large, frequently reused
content such as:

- A substantial shared curriculum corpus.
- A long grading rubric used unchanged across many calls.
- Large reference documents or media queried repeatedly.
- Stable product instructions that exceed the practical implicit-cache
  threshold.

Do not use explicit caches for ordinary short lesson prompts or rapidly changing
conversation state.

Before implementation, document:

- Supported model and location.
- Minimum content size.
- Expected request volume and break-even point.
- Cache creation and storage price.
- TTL and deletion behavior.
- Server prompt-template requirements in Firebase AI Logic.
- Authorization boundary for every user that can reference the cache.
- Behavior when the cache expires or is unavailable.

Cache creation and management must happen through a trusted backend workflow,
not through ad hoc browser code.

## Phase 5 — Add narrowly scoped application response caches

**Risk:** Medium to high

Only consider response caching after provider caching is measured and optimized.

Good candidates:

- TTS audio from identical normalized text, voice, speed, and language inputs.
- Versioned lesson artifacts that are identical for every learner in the same
  curriculum configuration.
- Prepared RPG scaffolding whose complete generation inputs are known.
- Deterministic translations of versioned static product copy.

Poor candidates:

- Tutor or Conversation replies.
- Adaptive questions based on learner history.
- Answer grading, safety classification, or proficiency scoring.
- “Next activity” decisions.
- Explanations that depend on the learner's mistake.
- Any response whose freshness or randomness is part of the experience.

Required response-cache key dimensions may include:

```text
environment
feature and artifact type
prompt-template version
curriculum/content version
provider and model
target language
support language
CEFR level
lesson ID
activity mode
normalized source-input hash
generation-settings hash
```

If a dimension affects output, it belongs in the key.

Every response cache must define:

- Scope: session, device, user, lesson, or global.
- TTL.
- Maximum entries or storage size.
- Invalidation triggers.
- Schema validation on read.
- Fallback on missing or corrupt data.
- Privacy classification.

## Phase 6 — Rollout and quality gates

Use independent feature flags for:

```text
cache telemetry
cache-friendly prompt ordering
OpenAI cache keys
Gemini explicit caches
each application response cache
```

Roll out in stages:

1. Internal testing accounts.
2. Small production cohort.
3. One low-risk feature.
4. Broader eligible features after metrics remain healthy.

Compare treatment and control for:

- Time to first token.
- Total latency.
- Provider failure and fallback rate.
- Input-token cost.
- Cache-hit percentage.
- Output schema failures.
- Lesson-generation retry rate.
- Grading agreement on a fixed evaluation set.
- User-visible repetition or stale-content reports.

Rollback must be possible by disabling a flag. Disabling caching must restore the
normal uncached request path without a migration.

## Test matrix

### Provider prompt caching

- Two identical long-prefix requests produce a measurable cache read when the
  provider supports it.
- Changing only the final learner input preserves prefix eligibility.
- Changing the prompt-template version avoids accidental key reuse.
- Short prompts continue to work without a cache hit.
- A cache miss returns the same response shape as a cache hit.
- Streaming and fallback behavior remain functional.
- Provider usage metadata is absent or malformed without breaking the request.

### Application response caching

- Exact inputs return the valid cached artifact.
- A language, level, lesson, model, template, or curriculum change misses.
- Expired entries miss and are replaced.
- Corrupt entries are discarded safely.
- Storage limits evict old entries.
- Two simultaneous misses deduplicate generation where appropriate.
- One user's private artifact cannot be read by another user.
- Offline/browser storage failure does not block model generation.

### Quality and UX

- Tutorial lessons remain beginner-appropriate.
- Tutor replies still reflect the current turn and learner state.
- Grading uses the current answer and current rubric.
- Generated lessons remain varied where variation is intentional.
- No cached artifact references removed or renamed curriculum content.

## Success criteria

Caching work is successful only when it demonstrates:

- Lower median and p95 model latency for targeted operations.
- Lower uncached input-token volume and cost.
- No increase in provider errors or fallback rate.
- No regression in schema validity or fixed-set evaluation quality.
- No increase in stale, cross-language, cross-level, or cross-user content.
- No unbounded browser, Firestore, or user-document growth.

Do not set a universal cache-hit target. Each operation should justify caching
based on its prompt length, prefix stability, volume, and quality requirements.

## Suggested implementation sequence

1. **PR 1:** Validate model configuration and add provider/model attribution.
2. **PR 2:** Add cache-token and latency observability.
3. **PR 3:** Inventory and version the highest-volume prompt templates.
4. **PR 4:** Reorder one stable OpenAI prompt family and measure it.
5. **PR 5:** Add an OpenAI cache key for that family if metrics justify it.
6. **PR 6:** Repeat the measured approach for one Gemini prompt family.
7. **Later PRs:** Evaluate explicit Gemini or response caching individually.

Each PR must be independently deployable and reversible.

## Open decisions for the implementation session

- Where should privacy-safe cache telemetry be aggregated?
- Which three operations have the highest repeated input-token cost?
- Does the active Gemini model name need correction before measurement?
- Which prompt prefixes are actually identical across users and lessons?
- Is any explicit Gemini cache large and frequently reused enough to beat its
  creation and storage cost?
- Which existing response caches need content-version invalidation or size
  limits?
- What retention policy is acceptable for provider and application caches?
